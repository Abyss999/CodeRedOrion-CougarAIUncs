# Food Waste Reducer — agent rules

Hackathon project (AI × sustainability/climate). iOS app that tracks fridge/pantry food, predicts
expiry, flags spoilage from photos, suggests recipes from expiring items, and lets friends/groups
share surplus. **Removing food with an outcome is how waste is measured** — it drives the Impact
Dashboard (food saved, money saved, CO₂ avoided). Product detail: [`docs/IDEA.md`](docs/IDEA.md).
Current state: [`HANDOFF.md`](HANDOFF.md).

## Rules
- **Secrets live in `.env` only.** Never hardcode or commit them, never print full keys. `.env` is
  gitignored; keep `.env.example` current with placeholders whenever you add a variable.
- **Run the backend from the project venv (`.venv` at the repo root)**, never the global
  interpreter. Install packages into the venv only, and pin them in `backend/requirements.txt`.
- **Any change to architecture, endpoints, schema or setup is reflected in `docs/` in the same PR.**
- **Keep `HANDOFF.md` current** — update it at the end of every work session.
- Small, reviewable commits with clear messages. Feature branches, PRs into `main`.
  **Never push directly to `main`.**
- **Verify before claiming done:** run the code, hit the endpoint, build the app. A builder's own
  check doesn't count; **QA sign-off does.**

## Stack
| Layer | Choice |
|---|---|
| iOS | SwiftUI, iOS 17+, project generated by **XcodeGen** from `ios/project.yml` (the `.xcodeproj` is gitignored), TestFlight for distribution |
| API | Flask (app factory in `backend/app/`), SQLAlchemy + Flask-Migrate (Alembic), gunicorn in Docker |
| DB | PostgreSQL with **TimescaleDB** (Tigerdata) — one database; `food_events` is a hypertable |
| AI | Google Gemini (recipes, voice/text parsing, expiry inference, vision fallback) |
| Vision | YOLO (Ultralytics — confirm the exact version before training, record it in `docs/DECISIONS.md`) |
| OCR | `zai-org/GLM-OCR` for receipts |
| Runtime | Docker Compose (`api` + `db`), ports bound to `127.0.0.1` |

## Multi-agent process
- The **Opus orchestrator** plans, fans out **Sonnet** builders for independent work, reviews, and
  owns all git (branches, commits, PRs). **Sub-agents never run git.**
- **Never let two agents edit the same file at once.** Ownership is the table above; anything
  outside your paths goes back to the orchestrator as a request.
- Each builder works in its own git worktree. Its paired QA agent starts **at the same time** in
  the same worktree and writes only in its own QA paths, so it tests the code as it changes.
- **One heavy run at a time** (Docker builds, full test suites, model inference). Parallel runs
  have run machines out of memory before. **Watch the disk too:** the TimescaleDB image alone is
  2.7 GB, and pulling it onto a nearly full shared server filled the disk on 2026-10-10.
- **Backend tests own `TEST_DATABASE_URL`.** The suite drops and rebuilds that schema and holds an
  advisory lock while it runs. Builders use `DATABASE_URL` for their own checks and never touch
  the test database.

## QA process and the merge gate
- Pairs: **Backend QA**, **iOS QA**, **ML QA** run alongside their builder; **Integration QA** runs
  after builders merge. QA writes and runs tests, checks each feature against its definition of
  done, and reports bugs to the orchestrator and the builder. **QA never edits feature code.**
- Each QA agent logs to `docs/qa/<area>.md`; the orchestrator folds it into
  [`docs/QA.md`](docs/QA.md) (sign-off log + bug list with severity, repro, status).
- **Merge gate:** a PR merges only with a QA pass recorded in `docs/QA.md` (what was tested,
  result, open bugs). A QA failure goes back to the builder — never merged around, never skipped.
- **Anything that breaks the demo path is a blocker:** add food by photo → expiry prediction →
  remove it → dashboard updates. Pass thresholds live in `docs/QA.md`.

## Core feature: removal = waste tracking
- Removal is a **soft delete**: `removed_at`, `outcome` (`used` | `donated` | `thrown_out`),
  `waste_reason` (`expired` | `didnt_like` | `forgot` | `other`) — **required for `thrown_out`,
  rejected otherwise.**
- Every removal writes a `remove` event to the `food_events` hypertable in the **same
  transaction** as the soft delete. A `donated` removal of a shared item fulfils its listing.
- Impact numbers are computed from `food_events`, never stored as running totals.
- Details: [`docs/SCHEMA.md`](docs/SCHEMA.md), [`docs/API.md`](docs/API.md).

## Design and UI
- **Design first:** key screens are produced on a Claude Design canvas with taste-skill
  (https://claude.ai/artifact/ALmB8FYKGrayhDQXqvoncx), mirrored into `docs/design/screens/`, and
  **approved by the team before iOS builds them** (record the approval in `docs/design/README.md`).
- Claude Design output is not SwiftUI — translate each design into native views, and take every
  color, spacing and type value from `ios/App/Theme.swift`, which mirrors
  [`docs/design/DESIGN_SYSTEM.md`](docs/design/DESIGN_SYSTEM.md). No ad-hoc hex values in views.
- **Never run Impeccable while generating UI.** UI review (Impeccable critique → polish, then
  web-design-guidelines) runs **once, at the end**, when the UI is feature-complete; iOS QA then
  re-runs the full UI suite.

## Conventions
- Python: Flask blueprints per area under `backend/app/routes/`, business logic in
  `backend/app/services/`, external calls (Gemini, ML service, OCR) behind one service module each
  so tests can stub them.
- API: JSON, `snake_case` keys, ISO-8601 UTC timestamps, JWT bearer auth, errors as
  `{"error": {"code": "...", "message": "..."}}` with a correct status code.
- Swift: one view per file, an `APIClient` protocol with a mock implementation for previews/tests.
- Tests: `backend/tests/test_<area>.py`; iOS `ios/Tests/UnitTests` and `ios/Tests/UITests`.
